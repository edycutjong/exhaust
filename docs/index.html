Six parts. The build is the checker.

The model is ordinary Fe, the checker is the compiler you already run, and the contract calls the function that was checked. A Python oracle, written separately, re-counts every pin.

A const fn walks the graph

Breadth-first search with while loops, mutable locals and array writes, evaluated by the compiler. Each successor is checked before it is encoded.

Take Fe out and the checker is gone.

Since Fe 26.1.0 (changelog) a const fn may loop, keep mutable locals and write into arrays, and static_assert evaluates it during the build. That is the whole move: the search is ordinary Fe, the build is the checker, and the same step() is called by the contract's recv handlers and by fe test on Sonatina and native.

We did not compare this against other contract languages or model checkers. This page describes what this build does, not how it ranks.

Notice to drivers · honest by design

What this does not prove.

  • Only the stated capacities are explored (C = 21 for the state count, C′ = 19 for the printed trace); behaviour above them is not checked. Liveness is not checked, only safety invariants.— README · Limitations
  • The escrow model has no caller identity: msg.sender authorization is not modelled. Units are abstract counters: no ETH or token moves, so value transfer, reentrancy and gas are out of scope.— README · Limitations
  • MODEL.md, the Fe model and the oracle share one author and one reading of the protocol. … A misreading shared by all three is not caught.— README · Limitations (excerpt)

Questions a judge would ask.

Is this formal verification?

No. It is bounded-exhaustive checking: every reachable state of the model at the stated capacity (escrow C = 21, vault B = 10 with T = 3) is explored at compile time. Above the bound nothing is checked; the bet is the small-scope hypothesis, that most protocol bugs already show at small sizes. For the nine bugs planted here it held: the oracle finds each one at escrow capacity 1 or 2, or vault balance 1 or 2, and the demo route 11234 is the same at capacity 2 as at 21 (evidence/small-scope.txt). C = 21 is how far one assert can count, not what the demo bug needs.

Why stop at capacity 21?

The state encoding holds at most 21 units (MAX_CAP = 21), and the C = 21 search already uses 940,335 of the 1,000,000 steps one assert may spend. The route printer runs at C′ = 19 (90.8%); C′ = 20 would still fit at 98.4%.

Can I raise the step budget?

Not in Fe 26.6.0: the limit is a constant in the compiler, with no flag or config. What works is splitting the search into independent asserts, each with its own million. Chaining consts does not help, because consts that reference other consts share one budget.

Is the deployed contract the code that was checked?

For the escrow, yes: its recv handlers call the same step(), and a differential test replays every reachable transition through deployed contracts (1,008 deployments, 25,646 handler calls), comparing ok and the stored state each time. The vault's caller and timelock checks are adapter code outside the compile-time check; the README lists exactly what is untested.

How does this relate to SMTChecker, Foundry, Echidna or halmos?

We did not benchmark against any of them. Solidity's compiler ships SMTChecker, which reasons symbolically with SMT and Horn solvers; Foundry invariant tests and Echidna run random call sequences and check invariants after each call; halmos tests EVM contracts symbolically. exhaust is an explicit-state search in ordinary Fe: no solver, no annotation language, no random sampling. The compiler enumerates every reachable state at a stated capacity, over the same step() the contract calls.

Who checks the checker?

An independent reference model in plain Python (tools/ref_model.py, stdlib only) recomputes every count; it agrees with all 15 Fe pins and the 3,680-row escrow edge table. It shares the author and one reading of the protocol, which the limitations say plainly.

How do I reproduce it?

Install fe 26.6.0 (5b3f96a), then fe build, sh demo/run.sh, fe test and fe test --backend native. DEMO.md maps every number to its command; a clean clone on Linux x86-64 reproduces the build and both test runs; the native backend needs a C linker such as gcc with libc6-dev (evidence/repro-linux-2026-11-21.txt).

Clone it. Break it. Watch the build refuse.
